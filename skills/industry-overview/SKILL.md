# Industry Overview

用于回答“帮我了解/总览/分析某个行业”的请求。目标不是堆资料，而是把行业讲成一张可决策的地图：边界清楚、结构完整、证据可追溯、结论有轻重。

## 非协商执行门槛

- 第一轮必须先完成计划，不得直接调用 `web_search` / `web_fetch` / `data_source_search` 开始取证。
- 计划阶段必须先界定行业范围、拆解行业总览子问题、审视修订，并写入本轮运行目录的 `plan.md`。
- 只有 `plan.md` 已包含子问题、研究问题、依赖关系与研究类型后，才可以开始搜索或抓取。
- 计划表中的每个研究步骤都必须由独立 sub-agent 执行；主 Agent 不得直接代替任一步骤做主体研究。
- 每个研究步骤都必须产出对应的 `findings/Sx.md`。即使步骤受阻，也必须写入该文件并说明 blocked 原因、已核查来源与剩余缺口。
- 所有必需的 `findings/Sx.md` 存在并被主 Agent 阅读前，不得写最终 `findings.md` 或向用户宣称行业总览完成。
- 主 Agent 只能做计划、调度、依赖摘要、验收、补充核验和最终综合；补充检索不得替代任何计划步骤的 sub-agent 产出。
- 完成最终 `findings.md` 后，必须向用户发送总结消息，包含核心结论摘要、最终文件链接、各子任务 findings 链接，以及任何证据不足或流程偏离。
- 在带有 session runtime 目录的 Web UI 中，当前工作目录通常已经是本 session 的输出目录。每一轮 industry-overview 必须在当前 session 输出目录内新建一个 `industry_overview_N/` 运行目录，N 从 0 开始选择最小未使用编号。所有运行时产物必须写入该目录；不得写入 `skills/industry-overview/`、`_agent/skills/industry-overview/`，也不得在当前 session 输出目录下再次拼接 `temp/<session_id>/`。

## 运行目录

每轮 industry-overview 的目录结构固定为：

```text
industry_overview_N/
├── plan.md
├── findings.md
└── findings/
    ├── S1.md
    ├── S2.md
    └── ...
```

路径规则：

- 新一轮行业总览开始前，检查当前 session 输出目录下已有的 `industry_overview_N/`，选择最小未使用 N。
- 本轮后续所有 plan、子任务 findings、最终 findings 都必须使用同一个 `industry_overview_N/`。
- 给 sub-agent 的输出路径必须是 `industry_overview_N/findings/Sx.md` 这种相对路径。
- 不要使用 `skills/industry-overview/plan.md`、`skills/industry-overview/findings/Sx.md` 或 `temp/<session_id>/...` 作为运行产物路径。

## 默认范围假设

若用户没有说明区域、时间或用途，默认：

- 区域：全球视角，并在有显著差异时补充中国/美国/欧洲等重点市场。
- 时间：以最近 12-24 个月的公开信息为主，涉及周期性行业时拉长到完整周期。
- 用途：为商业判断服务，兼顾投资、战略和创业视角。
- 深度：中等深度，优先覆盖关键结构与判断，不追求百科全覆盖。

若行业名称有歧义，先提出最可能解释并写入计划假设；只有歧义会显著改变研究方向时才向用户追问。

## 数据源与取证工具

优先与运行时 `Preferred data source` 一致；它是默认取证偏好，不是硬性执行边界。

- `mid_platform`：优先用于研报、行业报告、公司材料、市场规模和竞争格局。
- `news`：优先用于最新政策、融资、重大事件、技术变化和公司动态；中文请求检索新闻时，先提炼英文关键词再搜。
- `forum`：用于捕捉一线反馈、客户痛点、渠道变化和行业非正式观点；必须标注观点属性，不能当作事实直接引用。
- `web_search` / `web_fetch`：用于开放网页发现、官方文件、监管文本、协会/机构报告、公司公告与具体页面阅读。

质量门槛：

- 市场规模、增速、集中度、政策变化等关键事实，应尽量使用官方、协会、公司公告、权威机构或知名研究机构来源。
- 同一指标若口径冲突，必须说明口径差异，不要强行合并成单一数字。
- 对预测数据使用“预计/预测/机构口径”，并说明预测来源或不确定性。
- 论坛、媒体转述和无出处图表只能作为线索或补充，不能作为核心结论的唯一依据。
- 不暴露内部数据 ID、检索结果 ID 或无关运行细节。

## 执行流程

### A. 计划

1. 定义行业范围。
   明确行业名称、同义词、英文关键词、产品/服务边界、客户类型、B2B/B2C/B2G 属性、区域范围、时间范围，以及是否聚焦某类玩家或某个环节。
2. 判断用户用途。
   识别用户真正需要的是行业地图、投资机会、创业切入、竞争格局、市场规模、政策风险还是入门科普。用途不同，子问题权重不同。
3. 拆解为 4-5 个高价值行业总览步骤。
   默认步骤为：
   - S1 行业定义与价值链：边界、核心需求、上下游、参与者、利润池和议价权。
   - S2 市场规模与增长：规模、增速、渗透率、周期位置、需求和供给驱动。
   - S3 商业模式与关键指标：收入模式、成本结构、单位经济、定价机制、现金流和领先指标。
   - S4 竞争格局与壁垒：玩家类型、代表公司、集中度、差异化基础、进入壁垒和替代威胁。
   - S5 政策、风险与机会：监管、技术路线、供应链、宏观约束、未来趋势和 1-3 年机会。
4. 审视并修订步骤规划。
   检查是否存在维度缺失、步骤重叠、逻辑薄弱或不必要依赖；行业高度特殊时可替换默认步骤，但最终步骤数量必须小于 6。
5. 为每个步骤构造一个精确研究问题。
   问题必须清晰、完整、无歧义，足以驱动 sub-agent 独立取证，不依赖隐含指代。
6. 评估步骤间依赖关系。
   默认 `depends_on` 为 `[]` 以便并行；只有后续问题确实依赖前序 findings 的事实结果时，才设置依赖。
7. 为每个问题分类研究类型。
   可选类型：`Industry / Supply Chain`、`Enumeration`、`Comparison`、`Framework-led Analysis`、`Risk`、`Timeline`、`Geography`、`Relations / Network`、`Causal Attribution`、`Planning / Strategy`。
8. 将计划保存为本轮运行目录下的 `plan.md`。如果 `findings.md` 已存在，则清空该文件。
9. `plan.md` 必须包含 Task Table，列为：
   `| id | task | question | depends_on | research_type |`
   `depends_on` 空值统一写 `[]`。

### B. 并行执行

1. 主 Agent 阅读 `plan.md`，判断哪些步骤互不依赖，可以同时执行。
2. 对没有相互依赖的步骤，必须使用 `spawn` 并行启动 sub-agent；只有工具不可用或明确失败时，才允许降级，并必须在最终总结中说明原因。
3. 每个 sub-agent 只负责一个明确子问题，并应获得：
   - 行业范围、区域、时间窗口和用户用途
   - 对应研究步骤和研究问题
   - 研究类型
   - 运行时 `Preferred data source`
   - 必要的依赖步骤摘要
   - 明确的输出文件路径，优先使用 workspace-relative 路径
   - 完成条件：必须写入并读回验证该步骤的 `findings/Sx.md`
4. 每个 sub-agent 自行决定关键词、来源切换、放松策略和迭代深度；主 Agent 不预设固定搜索轮次。
5. 每个 sub-agent 仅写自己的 `industry_overview_N/findings/Sx.md`，不得写总 `findings.md` 或最终报告。
6. 主 Agent 发给 sub-agent 的 prompt 必须包含以下完成契约：
   - 将研究结果写入指定的 `findings/Sx.md`。
   - 写入后必须使用 `read_file` 读取该文件，确认文件存在且内容是本步骤结果。
   - 任务完成条件不是返回消息，而是指定 findings 文件存在、非空、可被 `read_file` 读回，并且内容属于本步骤。
   - 若搜索、抓取或证据不足导致步骤受阻，也必须写入 blocked 版本的 `findings/Sx.md`，说明受阻原因、已核查来源和剩余缺口。
   - 如果 `findings/Sx.md` 未成功写入并验证，不得声明 completed / done / success。
   - 不要用 `exec` 检查、读取或枚举 findings 文件；使用 `read_file`、`write_file`、`glob`。
7. 若步骤受阻，sub-agent 必须写入以下 blocked 版 `Sx.md` 模板：

```md
# Sx: <任务名>

## Status
blocked

## Blocker
<搜索、抓取、权限、证据不足等阻塞原因>

## Sources Checked
<已实际检查的来源、工具结果或查询方向>

## Partial Findings
<已经能确认的信息；没有则写“无可确认结论”>

## Remaining Gaps
<还缺哪些证据或后续应如何补证>
```

8. sub-agent 完成时只需给出以下结构化完成信号，实质结果以 `findings/Sx.md` 为准：

```text
status: done | blocked
findings_file: industry_overview_N/findings/Sx.md
verified: yes | no
note: 一句话说明
```

   `verified: no`、缺少 `findings_file`，或完成信号与文件状态不一致时，主 Agent 不得视为完成。
9. 主 Agent 在 sub-agent 完成后必须使用 `read_file` 读取对应 findings 文件；若文件不存在、为空、不是该步骤结果，或未包含 `Status`，应将该步骤视为未完成。
10. 未完成时，主 Agent 最多重新派发同一步骤一次。重派 prompt 必须明确要求先补写/修复指定 `Sx.md`，不得继续泛泛研究；若补写仍失败，主 Agent 必须自行写入 blocked 版 `Sx.md`，说明“subagent 未能交付文件”，并在最终总结中披露流程偏离。
11. 对存在依赖关系的任务，按依赖波次执行：先并行启动所有依赖已满足的任务，等待并读取对应 `findings/Sx.md`，再启动下一批任务。
12. 每批结果完成后，主 Agent 可更新 `industry_overview_N/findings.md` 草稿；最终版本必须在所有步骤验收后完成。

### C. 产出报告

仅在必需步骤 `done`（或有充分理由 `blocked`）后出最终结论。报告必须区分事实、机构预测和推断，并附来源链接。报告中不允许出现任何数据 ID。

默认输出结构：

```md
# <行业>行业总览

## 一句话结论
<用 2-4 句话说明行业本质、当前阶段、主要机会与最大风险。>

## 1. 行业定义与边界
<行业包括/不包括什么，核心需求与客户是谁。>

## 2. 价值链与利润池
<上中下游、关键环节、议价权、利润集中位置。>

## 3. 市场规模与增长
<规模、增速、渗透率、周期位置；明确口径和来源。>

## 4. 商业模式与关键指标
<收入、成本、单位经济、定价、现金流，以及最该跟踪的指标。>

## 5. 竞争格局
<玩家类型、代表公司、集中度、壁垒和替代威胁。>

## 6. 政策/技术/风险
<监管、技术路线、供应链、宏观或需求风险。>

## 7. 未来趋势与机会
<1-3 年趋势、受益环节、进入切口、验证信号。>

## 关键不确定性
<列出证据不足、口径冲突或需要继续跟踪的问题。>

## Sources
<列出实际核查过且支撑核心结论的来源。>
```

写入最终 `industry_overview_N/findings.md` 后，必须发送用户可见的完成总结，包含最终报告文件链接和所有 `findings/Sx.md` 子任务文件链接。

## 质量底线

- 先界定范围，再开展搜索。
- 子问题必须并行 sub-agent 化；不要把行业总览退化成主 Agent 单线程资料汇总。
- 不得引用未实际核查的来源。
- 相比浅层广覆盖，优先完整且可决策的行业结构。
- 证据薄弱、混杂或过时时，必须直接说明。
- 市场规模和增速必须说明口径、时间和来源；口径冲突时保留冲突而不是强行合并。
- 结论必须解释“为什么重要”和“对用户判断意味着什么”。
